# 工作流详解

本文逐个展开六个阶段：每个阶段的输入、动作、产出与门禁。

## 总览

| # | 阶段 | Skill | 主要产出 |
|---|---|---|---|
| 01 | 原著分析 | `short-drama-novel-analyze` | 章节索引、功能提取、分集候选 |
| 02 | 开发立契 | `short-drama-develop` | 创作简报、故事引擎、分集地图 |
| 03 | 剧本写作 | `short-drama-write` | `剧本.md` |
| 04 | 视觉设定与资产 | `short-drama-assets`、`short-drama-image-prompts` | `视觉设定.md`、`图片提示词.md` |
| 05 | 分镜与运动提示词 | `short-drama-storyboard`、`short-drama-video-prompts` | `分镜.md`、`视频提示词.md` |
| 06 | 生产与审查 | `short-drama-produce`、`google-flow-manga`、`short-drama-review` | 制作成果、Flow 包、审查报告 |

---

## 01 原著分析

**输入**：原著全文（`输入/`，只读）

**管道**：S0 → S5 六阶段

| 阶段 | 做什么 | 产出 | 停靠条件 |
|---|---|---|---|
| S0 | 建章节索引 | `_index.json`、`_progress.md` | 索引有问题就停 |
| S1 | 改编价值快评（抽样） | `triage.md` | **停靠问创作者** |
| S2 | 逐章功能提取 | `chapters/ch-<N>-extract.md` | 覆盖率不足就停 |
| S3 | 剧情单元与节奏聚合 | `story-units.md`、`rhythm-and-emotion.md` | 阈值不达标就复核 |
| S4 | 人物归并与设定 | `characters.md`、`world.md` | — |
| S5 | 改编价值与分集候选 | `adaptation-value.md`、`episode-candidates.jsonl` | 交接 develop |

**关键约束**

- 索引是**唯一切片真源**。每个阶段各跑一次正则，会切出互相对不上的章节，第 47 章按一种边界分析、按另一种边界聚合，而且没有人会发现。
- 分析永远是**候选**。哪条线保留、哪些人合并、从哪里开篇，是创作者的决定，由 `develop` 立成改编契约。本阶段不批准自己的产物。
- S2 覆盖率不足时**不得进入 S3**。聚合会照样产出一份读起来完整的结果，而缺掉的章不会在任何地方留下痕迹。
- 单章连续失败两次就标记跳过并记录，在后续每份聚合产物里注明该章缺失。**失败可以接受，失败被藏起来不行。**

**门禁**：索引覆盖率校验、span 可证明性；S1 快评后停靠创作者决策。

## 02 开发立契

**输入**：原著分析产物，或创作者的梗概/想法

**动作**

1. **锁定创作者契约** —— 区分不可改的事实、可探索的空白、形式约束与制作边界。
2. **探索真正不同的方向** —— 提出机制不同的候选（改变主角策略、对抗来源、代价或冲突方式），而不是换标题、职业和措辞。
3. **建立故事引擎** —— 压力如何出现、主角如何应对、对手如何反制、每轮冲突改变什么、哪种转变会终结这个引擎。
4. **把系列运动落到分集** —— 每集记录进入状态、开场、当集追求、阻力、方向性转折、当集结果、信息释放、出去的压力与下一集必须继承的事实。

**产出**

- `项目开发/creative-brief.md`
- `项目开发/story-engine.md`
- `项目开发/director-brief.md`（需要时）
- `项目开发/adaptation-map.jsonl`（长材料改编时）
- `项目开发/episode-map.jsonl`

**门禁**：引用可追溯、未决项显式标记。集数、钩子类型、是否反转和高潮位置由创作者与项目决定，不用固定配方替代因果判断。

## 03 剧本写作

**输入**：本集在分集地图中的位置与交接事实，或创作者的直接要求

**动作**

1. 锁定本集承诺的观看体验、谁现在要什么、阻力、当集兑现和退出状态。
2. 只识别本集实际存在的发动机，不强行补齐。
3. 排「因为 → 行动 → 结果 → 下一股压力」，不落盘节拍表。
4. 逐场确定不可替代的功能、可见变化与场尾状态。
5. 把动作、对白、画外音、声音事实和画面文字写入同一份剧本。

**产出**：`episodes/<EP>/剧本.md`

格式约定：

- 一级标题 `# EP001 集名`
- 场景标题 `## EP001-SC001 内 · 地点 · 时间/天气`
- 对白 `角色（可选表演提示）：台词`
- 生产标签 `[VO]`、`[OS]`、`[SFX]`、`[画面文字]`、`[连续性]`、`[转场]`

**写作要求（节选）**

- 每场改变信息、权力、关系、情绪、物理状态或风险；无变化的场删掉或合并。
- 对白必须在争取、回避、试探、逼迫或重新定义关系。
- 核心阻力的转向要有可追溯的事实、筹码、权限、代价或人物行动，不能只靠对手停止反应。
- `[连续性]` 只交接由前文动作已经建立、又容易在下游丢失的状态。

---

## 04 视觉设定与资产

**输入**：当前范围的剧本、已决定的视觉方向

**动作**

1. 逐场找实体、可见描述、状态变化和含混指代，**先不创建资产**。
2. 对每项决定新建、复用、增加变体或标记未决；含混指代不猜。
3. 写最小可识别设定：统一使用「识别锚点」、本集状态和变化原因。
4. 检查造型/伤势、持物/所有权、道具状态、地点时段/天气/光态与跨集 outgoing。

**核心区分**

| 类型 | 判据 | 处理 |
|---|---|---|
| **身份** | 换一个就不再是同一个人、地或物 | 新建资产 |
| **变体** | 身份不变，但服装、伤势、时段、天气、开合或持有状态改变 | 增加变体 |
| **镜头瞬态** | 姿势、视线、左右手、站位、相机角度 | 由分镜拥有 |
| **故事语义** | 知识、目标、关系和情绪 | 由写作/开发拥有，只引用可见后果 |

**产出**

- `episodes/<EP>/视觉设定.md`（`short-drama-assets`）
- `episodes/<EP>/图片提示词.md`（`short-drama-image-prompts`）

图片提示词每项用 `IMG-...` 标题，正文放在 `### 可复制提示词` 引用块。`IMG-...` 只是该提示词条目的稳定 ID，**不声明图片已生成或可用**。

---

## 05 分镜与运动提示词

**输入**：当前剧本、必要视觉事实

**动作**

1. 确认每个场景动作、对白、声音、画面文字和转折由哪些镜头承载。
2. 确定观众何时知道什么、对齐谁、空间如何揭示、转折落在哪个可见动作。
3. 每镜写清唯一职责、来源、时长、景别/机位、起点、终点、声音和视觉依据。
4. 锁定人物朝向、位置、视线、持物、出入口、屏幕方向和必要状态。
5. **冻结关键帧只投影镜头起点** —— 删除终点才出现的文字、动作、姿态或道具状态。

**产出**

- `episodes/<EP>/分镜.md` —— 每镜二级标题 `## SHOT-...`，其下 `### 冻结关键帧提示词`
- `episodes/<EP>/视频提示词.md` —— 每镜 `MOTION-...` 标题并引用对应 `SHOT-...`

**两条独立的引用轴**

- **图片提示词项** —— 指向 `图片提示词.md` 的 `IMG-*` 条目，代表「计划用这张提示词生成资产」
- **输入参考图** —— 创作者已提供或经确认生产的**实际图片**，用 `REF-*` 槽位引用

两者可以独立组合：有合法的图片提示词项时，输入参考图仍可为「无」。

**门禁**：轴线、站位、视线、持物连续性；切镜必须带来信息、权力、情绪、空间或节奏变化。

## 06 生产与审查

### 生产（`short-drama-produce`）

**四步硬闸门，顺序不可合并：**

1. **建立有边界的 job** —— 一种 modality、明确数量、完整 prompt/spec、参考文件、参数、输出路径与 adapter profile。
2. **`prepare`** —— 展示完整预览（数量、prompt、source entry、reference bindings、outputs、overwrite、adapter），不调用供应商。任一漂移 fail closed。
3. **`confirm`** —— 创作者在**看到预览之后**明确确认。只有明确同意这项当前任务才运行。
4. **`run`** —— 启动 adapter。成功或失败后再次执行都必须重新确认，防止失败重试意外产生第二笔费用。

**「继续」「都做完」「预算没问题」、上游内容已接受或之前确认过另一版，都不算本次生产确认。**

失败按三路走：技术失败（超时、限流、服务端错误）可做有上限重试；被拒输入（提示词、参考图、音频）先改那一项再投；重复内容缺陷回到对应 prompt/spec owner。

### Flow 生产包（`google-flow-manga`）

三种工作模式：

- `prepare` —— 创建或更新 Flow 交接包、状态台账和逐镜卡
- `preflight-review` —— 只检查现有生产包是否可进入 Flow，不改上游来源
- `output-review` —— 检查已生成片段，记录接受/重做结论和正确修复层

每镜按目标选择 Flow 输入模式：`ingredients`（身份/物件/场景引用是主要约束）、`frames`（构图或首尾状态是主要约束）、`text`（无可复用引用）、`video-edit`（基于已有片段修改）。

**不得登录、操控或自动提交 Google Flow**，不把「准备好了」「继续」当作付费生成确认。

### 审查（`short-drama-review`）

**结论四档**：`APPROVE` / `APPROVE_WITH_NOTES` / `REVISE` / `PROVISIONAL`

**严重程度四档**：`blocker` / `major` / `minor` / `note`

每条 finding 必须包含：位置、必要短引文或冲突事实、观众/制作影响、必须达到的修订结果、owner、严重程度和规则等级。

**不能只说「AI 味」「不够电影感」或给无证据分数。**

跨文档综合检查顺序：

```
剧本事实 → 视觉设定 → 镜头职责与边界 → 冻结关键帧 → 视频运动 → 下一状态
```
