# 设计原则

本文说明五个核心机制**为什么这样设计**——它们各自针对什么失败模式，以及替代方案为什么不够好。

---

## 一、文件系统即唯一真相

**做法**：每集只维护五份创作者可读的 Markdown。明确拒绝另建 episode card、beats 表、block index、录音表、QA 记录这类「并行的结构化真相」。

**针对的失败模式**：同一事实存在多处副本时，副本会分叉。分叉后无法判断哪份是真的，下游引用哪份都可能是错的。

**为什么不用数据库/结构化清单**：结构化清单对机器友好，但创作者读不了。创作者读不了的产物，创作者就无法审查；无法审查的产物，就只能盲信。工作流的全部价值建立在「创作者能看见并能否决」之上。

**代价**：Markdown 的机械可校验性弱于结构化数据。这靠两样东西补上：`references/*.md` 里明确到字段级的格式约定，以及 `scripts/*.py` 里的解析校验器。

---

## 二、连续性来自显式状态

**做法**：每个镜头必须写 `start_state` / `end_state` / `continuity_delta`，任何可见变化都要有 `why_changed`。

**针对的失败模式**：生成式模型没有跨镜头的持久记忆。如果连续性依赖「模型记得上一镜角色穿什么」，那么在第 40 个镜头时它一定会漂移，而且漂移是**静默**的——没有任何地方会报错。

**为什么这样设计**：连续性不能依赖模型的隐式记忆。改成写在文件里的显式契约后，漂移就变成可检测的状态矛盾：

```
单帧好看不能覆盖序列错误。
无法用脚本、前镜、世界规则或明确设计锁解释的变化，视为连续性风险。
```

**关键判据**：连续性门禁逐镜检查五个状态轴——人物身份/发型/服装/伤势/持物/知识/意图；地点/内外/昼夜/天气/光源/空间关系；道具位置/状态/数量/文字/损坏/所有权；左右位置/视线/动作方向/景深/轴线；当前剧情阶段。

## 三、owner 边界

**做法**：每个 Skill 只写自己的产物。发现上游有问题时，写审查报告并路由回正确的层，而不是顺手改掉。

**针对的失败模式**：多环节交叉修改。A 改了 B 的产物，B 下次运行时会把它覆盖掉；或者 B 基于被污染的输入继续工作。两种结果都会让状态无法推理。

**具体约束**：

- 审查与修改是两个独立工作单元，审查**不在同一轮替 owner 改来源**
- 生产结果不自动回填分镜；需要时由分镜 owner 修订文档，再建立新 job
- 开发 Skill 不直接改写 creator authority 配置，只产出候选并由路由 Skill 提升

**为什么严格**：这不是洁癖。当「谁能改什么」没有结构约束时，任何一次并行或异步执行都可能产生不可复现的状态。owner 边界是把「可复现」从愿望变成结构保证的手段。

## 四、机械门禁 + 人类停靠

**做法**：能证明的交给脚本，需要判断的交给人类。两者严格分离。

**机械门禁的特征**：

- 可离线运行，不需要网络
- 结果是二值的（通过 / 不通过）
- **fail closed** —— 错误则停下，绝不带着错表进入下一阶段
- 覆盖：索引覆盖率、引用完整性、ID 一致性、包结构、提示词边界

典型例子：S2 覆盖率不足时**不得进入 S3**。因为聚合照样会产出一份看似完整的结果，缺掉的章却不会留下任何痕迹。这类「看起来正常的错误」必须由门禁拦住。

**人类停靠的特征**：

- 只在真实创作分叉点触发，不用 schema、目录、事务或检查器询问创作者
- 必须显式确认，含糊的同意不算
- 典型：S1 快评后（是否继续全量拆解）、生产确认（是否花这笔钱）

**为什么必须分离**：如果脚本能否定创作选择，工具就凌驾于创作者之上；如果主观偏好能伪装成硬性约束，创作者就被迫服从于工具作者的口味。分离之后，机器只负责「证明」，人负责「判断」。

## 五、规则四级分级

**做法**：把规则按阻断权限分成四级。

| 级别 | 含义 | 阻断权限 | 例子 |
|---|---|---|---|
| `structural_invariant` | 本地可证明的引用、ID、显式状态矛盾 | 脚本可阻断 | 索引覆盖率不足、引用指向不存在的资产 |
| `reviewed_invariant` | 语义义务：升级是否真实、承诺是否兑现 | 审查带证据判定 | 结尾把主动角色改成被动沉默却没有因果收益 |
| `craft_default` | 通常有帮助的做法 | 创作者说明理由后可覆盖 | 每场必须改变某种状态 |
| `taste_option` | 创作选择 | 不得单独阻断 | 从哪里开篇、保留哪条线、结局气质 |

**针对的失败模式**：规则不分级时，要么所有规则都很硬（创作者被工具绑死），要么都很软（质量问题拦不住）。

**关键约束**：

- 不要用固定的章数配方、情节点数量或篇幅比例替代因果判断
- `taste_option` 不得单独阻断——它只能作为建议提出
- `craft_default` 被覆盖时必须记录理由

## 一条贯穿全部的原则：渐进披露

Skill 的 `SKILL.md` 只放路由与索引，详细方法论拆到 `references/` 下按需加载。因为把全部方法塞进主文件会让每次加载都付出全部上下文成本，而其中大部分内容在具体任务中根本用不到。

具体做法是：主文件里明确列出「出现什么信号时读哪一份参考」，而不是一次性全部读入。
